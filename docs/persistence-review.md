# 持久化选型复审（2026-09-06）

结论写在前面：**存储引擎继续用 SQLite，这一条不接近；访问层建议从手写 C API 封装迁移到 GRDB，并且建议现在做。**下面是支撑论据。

## 一、真实业务规模（实测，非估算）

压测代码在 `Tests/PolishStoreTests/Benchmark.swift`，默认不跑，`POLISH_BENCH=1 swift test -c release --filter benchmark` 复现。机器为本机 Apple Silicon，release 构建。

| 指标 | 实测 |
|---|---|
| 单行 upsert（每次独立事务，即真实写入模式） | 12,713 次/秒 |
| 101,000 行、每行约 4.3KB 正文的文件体积 | 453 MB |
| `recent(200)`，101,000 行 | 1.1 ms |
| `recent(200)`，500 行（保留上限） | 1.1 ms |
| `usage()` 全表聚合，101,000 行 | 39.8 ms |
| `purge` 从 101,000 行裁到 500 行 | 225.7 ms |

对照真实负载：单用户、菜单栏工具、快捷键触发。一次润色产生 2–4 次写入（每次状态变化一次）。按重度使用每天 100 次润色计，约 400 次写入/天 —— 折合 **0.03 秒的写入工作量**。保留策略上限 500 条，稳态文件约 2 MB。

读模式只有两种：窗口打开时取最近 200 条，以及按技能聚合的使用统计。两者都有索引覆盖（`records_created_at`、`records_skill`）。

**性能余量在 200 倍以上，且在 100 倍数据量下所有操作仍低于人眼可感知阈值。性能不是这个决策的判据**，任何一个候选方案都能轻松满足。真正的判据是可靠性语义、维护成本和演进方向。

## 三、决策一：存储引擎

保持 SQLite。约束它的不是数据量，是这四条语义要求：

1. **部分更新的原子性**。一次润色写 2–4 次，崩溃不能留下半个状态。JSON 全文件重写做不到增量原子性。
2. **集合操作**。保留策略要按年龄删行、按条数裁剪、按年龄清空正文，三步必须在一个事务里。文件方案要全量载入再全量写回。
3. **聚合**。按技能统计使用与命中，是「用得多的技能优先推荐」这个方向的输入。
4. **多进程可能性**。CLI 是独立进程，将来若也要记录，需要真正的跨进程锁。

被排除的：
- **UserDefaults / plist**：量级与查询能力都不匹配，且 plist 全量读写。
- **Realm**：MongoDB 已于 2025-09-30 结束支持，直接违反 AGENTS.md「维护活跃」判据。
- **SwiftData / Core Data**：系统框架，无依赖成本，但表达不了 `STRICT`、`CHECK`、部分唯一索引 —— 现有 60 项测试里有 12 项直接断言这些约束；也没有显式事务边界与 `BEGIN IMMEDIATE`；`ModelContext` 非 `Sendable`，而本项目写入来自后台任务、读取来自 `@MainActor`；macOS 上另有已知崩溃报告。这些恰好是本项目最在意的那一层。

## 四、决策二：访问层（真正有争议的部分）

### GRDB 能替掉什么

`Database.swift`（289 行）绝大部分、`Schema.swift`（103 行）的迁移器机制、`Stores.swift` 里的行解码（约 40 行）。约 **540 行会消失**。此外解锁四项现在没有、但方向上会需要的能力：`ValueObservation`（数据库驱动的界面刷新）、`DatabasePool`（读写并发）、FTS5（历史全文检索）、SQLCipher（落盘加密）。

### GRDB 替不掉什么

`STRICT`/`CHECK`/部分唯一索引的 DDL（在 GRDB 里同样是原始 SQL）、0700/0600 权限与符号链接拒绝、保留策略、中断恢复语义（`running`→失败、`applying`→uncertain）、领域映射与 `Outcome` 的磁盘契约。约 **400 行留下**，60 项行为测试基本全部继续适用 —— 它们测的是行为，不是实现。

### 为什么建议现在迁

1. **AGENTS.md 已经写明优先选用成熟第三方**。手写这层不属于「确无合适现成方案」，GRDB 就是那个方案。
2. **缺陷密度是实测数据，不是假设**。开发这 942 行的过程中，测试抓到三个真实缺陷，全部落在 GRDB 会接管的那 350 行里：`SQLITE_OPEN_NOFOLLOW` 会拒绝路径中任何一层符号链接（macOS 的 `/var` 就是）、打开失败时先关句柄再读 `errmsg` 读到已释放内存、`Duration.components.seconds` 把亚秒超时算成 0。它们都被测试拦住了，但同样说明：手写连接层在没有生产暴露的情况下，缺陷不在少数。GRDB 在这些路径上有多年生产暴露。
3. **现在是迁移成本的最低点**。942 行、60 项现成测试、没有任何外部代码依赖它的内部结构。往后每加一个功能这个数字只增不减。
4. **维护面转移**。SQLite 的接口弃用、Swift 并发模型的演进，由上游承担。

### 反方论据（如实列出）

- **今天没有任何功能性收益**。数据量、并发度、查询复杂度都远未触碰手写层的能力边界。
- **引入本仓库第一个第三方依赖**，带来供应链面与版本维护义务。
- **重写存储代码固有丢数据风险**。60 项行为测试把风险压得很低，但不为零。
- AGENTS.md 工程纪律同时写着「不要顺带加入重构、架构调整」。原则约束的是选型，追溯适用到已验证的代码需要单独的理由 —— 上面第 2 条就是那个理由。

## 五、建议与验收门槛

1. **引擎不动**。SQLite 保持。
2. **访问层迁移到 GRDB**，作为一次独立提交，不夹带任何功能改动。
3. **验收门槛**：`Tests/PolishStoreTests` 与 `Tests/TextPolishAppTests` 的 60 项行为测试**一行不改**全部通过。改测试即意味着行为变了，那就不是迁移而是重写。
4. 迁移后保留 `Benchmark.swift`，用同一组指标对照，确认没有性能回退。
5. 若决定**不迁**，同样是站得住的选择，但要把触发条件写进 AGENTS.md，任一成立即重启此议题：需要落盘加密；需要历史全文检索；CLI 或第二个进程也要写记录；需要数据库驱动的界面刷新；手写层再出现一个由并发或 SQLite 细节引起的缺陷。

## 六、一处已知的自觉取舍

文件模式下 `synchronous = NORMAL`。应用崩溃不丢已提交事务，但**操作系统崩溃或断电可能丢掉最近若干次提交**。对润色历史这是合适的取舍（丢的是记录，不是用户正文——正文在目标应用里）。若判断改变，`Database.swift` 里改成 `FULL` 即可，代价是每次提交多一次 fsync。

## 七、迁移结果（2026-09-06 当日完成）

### 验收门槛达成情况

102 项测试**一行未改**全部通过。改动只落在 `Package.swift`、`PersistenceError.swift`、`Database.swift`、`Schema.swift` 四个文件；所有测试文件的修改时间都早于迁移开始时间。

### 代码量：预估错了，如实记录

| | 迁移前 | 迁移后 |
|---|---|---|
| `Sources/PolishStore` 总行数 | 942 | 866 |
| 直接 SQLite C API 调用 | 遍布连接层 | **0** |

第四节预估「约 540 行会消失」，**实际只净减 76 行**。预估错在把收益当成了代码量。GRDB 实际替掉的是密度最高、风险最集中的那一部分：连接打开与 flags、语句的 prepare/bind/step/finalize、事务与保存点的裸 SQL、结果码与错误消息提取、以及手写的 actor 串行化。这些是三个已知缺陷的全部产地，但它们本来就不占多少行。

留下来的是项目特有的部分，任何库都替不掉：`SQLValue` 固定的落盘编码（日期是整毫秒、UUID 是字符串——GRDB 原生的 `Date` 转换会写 ISO-8601 文本，直接破坏现有契约）、按列名失败的解码、0700/0600 与符号链接拒绝、保留策略、中断恢复语义。

**结论修正：这次迁移的收益是风险转移，不是代码量。**判断一个第三方库值不值得引入，看它接管的代码的缺陷密度，不看行数。

### 性能对照（同一组压测，同一台机器）

初版本节写着「写入慢 12%」，**那个结论是错的，方法有问题**：两边各只跑了一次。补测 GRDB 自身的波动后：

| 指标 | 手写（n=1） | GRDB 7.11.1（n=6） | 判定 |
|---|---|---|---|
| 单行 upsert | 12,713/s | 11,196 – 12,652/s | 落在噪声内，**不构成差异** |
| `recent(200)` @101k 行 | 1.1 ms | 1.3 – 1.4 ms | 稳定复现的小差 |
| `usage()` @101k 行 | 39.8 ms | 41.7 ms | 单样本，不判定 |
| `purge` 101k → 500 | 225.7 ms | 222.2 ms | 单样本，不判定 |

「快 12%」是拿手写的单个样本去比 GRDB 六次里最慢的一次得出的。手写版本已被覆盖且从未提交，无法补测，所以写入侧只能给出一个诚实的结论：**在本机这组负载上测不出差异。**

`recent(200)` 的 0.2 ms 差是稳定的。我最初猜是连接池的读连接页缓存冷，做了 A/B：同一条 SQL，一次走池里的读连接、一次走写连接（页缓存热），三轮结果为 0.77/0.82、0.68/0.67、0.84/0.75 ms——**假设被推翻**。同一组实验顺带给出更有用的分解：只解码一列是 0.7 ms，解码完整 `PolishRecord`（9 列、两个大文本字段）是 1.3 ms，所以这条查询有一半时间花在行解码而不是查询本身。

剩下能解释那 0.2 ms 的机制是行物化：GRDB 的 `Row.fetchAll` 先把整行所有列拷进 `Row` 对象再交给调用方，手写版是在 step 循环里直接从活语句读列，没有中间对象。这个解释预测差距随行宽与行数增长、随只读少数列而消失——与数据一致，但**未单独验证，是机制解释而非实测结论**。

按真实负载（每天约 400 次写入、窗口打开时读一次）折算，以上任何一项差异都在每天几毫秒的量级。

### 打包影响

GRDB 带一个 `GRDB_GRDB.bundle`（只有 PrivacyInfo 隐私清单）。GRDB 运行时不读自己的资源包，缺失也不会崩，但签名后的 app 里应当带上，`scripts/package-app.sh` 已增加一行拷贝。

### 保留的自研部分

`Migrator` 没有换成 GRDB 的 `DatabaseMigrator`。原因：本项目要求「结构版本高于当前构建时拒绝打开」，而且用 `user_version` 而不是额外的迁移表，任何 `sqlite3` 客户端都能直接读出版本。剩下的 40 行编排逻辑跑在 GRDB 的 `write` + `execute` 之上，没有裸 C 调用，风险面已经和其它部分一致。
