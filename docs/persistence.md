# 持久化层设计

## 目标与边界

Dayi 桌面端将润色记录写入本机数据库；原目标句柄和撤回数据只放在本次运行的内存里，退出即清空。本层为需要跨重启存活的数据提供一个统一的落地方式：可编辑的技能（提示词模板）、润色记录、以及少量本机设置。

明确不做的事：

- 不存模型凭据。凭据仍然只来自进程环境或用户显式选择的本机配置。
- 不存目标句柄。AX 元素属于目标进程，随进程消失；存下来只会变成一个兑现不了的承诺。跨重启的「原位撤回」因此不成立，本层只保留原文与结果供人工取用。
- 不阻塞主流程。存储失败只降级为「这次不记录」，并把原因显示在任务窗口里，永远不让一次按键失败。

## 接入方式

`AppModel` 在启动后异步打开数据库，期间产生的记录先留在内存，打开后补写，因此启动瞬间完成的任务不会丢。任务状态每变化一次就写一次（同一任务是 upsert，一行），写入按调用顺序串行，避免两次更新乱序落地后文件描述的状态比屏幕更旧。

打开时做三件事：按保留策略清理、载入最近记录、**恢复中断状态**。上次运行留下的非终态行不是结果——`running` 记为失败（没有产生过正文），`applying` 记为 uncertain（写没写进去，这个进程已经无从证明），与项目既有的 uncertain 纪律一致。

任务窗口把本次运行的活动任务和历史记录分开显示。历史只能查看、复制和删除：AX 目标随进程消失，跨重启的「返回原位置」和「原位撤回」不成立，界面明说这一点而不是给一个按不动的按钮。

## 分层与职责

| 模块 | 负责 | 不负责 |
|---|---|---|
| GRDB 7 | 连接与连接池、语句预编译与绑定、事务与保存点、结果码 | 本项目的落盘编码与命名 |
| `Database` | 文件位置、拒绝符号链接、权限、把数据库错误翻译成领域错误 | 语句执行本身 |
| `SQLValue` / `Row` 扩展 | 固定日期与 UUID 的落盘编码；按列名失败的解码 | 业务含义 |
| `Session`（= GRDB 的 `Database`） | 一次事务内的同步读写视图 | 自己开事务、跨事务存活 |
| `Migrator` / `PolishSchema` | 版本化结构演进，版本号与结构同事务落地 | 数据语义校验 |
| `Skill` / `PolishRecord` / `RetentionPolicy` | 实体与保留策略的值语义 | I/O |
| `SkillStore` / `RecordStore` / `PreferenceStore` | 应用依赖的抽象契约 | SQL |
| `SQLite*Store` / `MemoryRecordStore` | 契约的两种实现 | 生命周期管理 |
| `PolishStorage` | 组合根：打开、迁移、装配 | 具体查询 |
| `DomainMapping` | 领域类型与存储类型之间的显式转换 | 领域规则 |

依赖方向单向：`PolishStore → PolishCore`。领域不知道存储存在，因此润色核心的测试可以在没有数据库的情况下运行。

## 数据模型

三张 `STRICT` 表：`skills`、`records`、`preferences`。约束尽量落在数据库里，因为文件是进程之外的边界，另一个进程或一次手工 `sqlite3` 操作同样能写它：

- `user_prompt_template` 必须包含 `{input}`，否则 `PromptTemplate.render` 无处放草稿。
- `name` 去掉空格、制表符与换行后不能为空。
- 活跃技能的名字唯一（部分唯一索引，归档后名字释放）。
- `outcome` 只接受七个已知取值；读取时再由 Swift 枚举校验一次。
- `records.skill_id` 外键；删除技能时置空，记录与正文保留。

时间统一存为毫秒整数：排序精确，往返无浮点误差。这也意味着亚毫秒精度会被丢弃，该行为由测试固定。

结构第 3 版给 `records` 增加可空的 `failure_json`：新产生的已知错误保存 `RecordedFailure` 的错误类型和参数，按当前界面语言显示。枚举 case 名称和关联值是持久化契约；损坏的 JSON 按解码错误报告。旧记录与未知外部错误继续保留原 `message`，不从已有文本猜测错误类型。

模型设置在 `preferences` 的 `model.profiles` 中保存配置集合与当前配置 ID，凭据只保存钥匙串 account 引用。旧 `model.profile` 读取后迁入集合，沿用其原钥匙串账户；新保存的凭据使用独立账户。模型请求在触发时固定配置，后续切换不改变在途请求。

本机提示词覆盖通过 `preferences.prompt.custom-skill` 引用 `skills.id`。编辑保存创建新技能修订、归档上一版并更新引用，三步同事务；恢复默认归档当前自定义修订并删除引用。旧技能正文保留供历史解释，不就地改写。每个任务固定自己的 skill ID，不用结果返回时的当前设置替换历史关联。

结构第 4 版给 `records` 增加可空的 `website_host`。它仅保存捕获时已确认的网站主机名，不包含协议、端口、路径、查询、片段或凭据；`target_label` 仍是原宿主应用名。旧记录保持 NULL，不推断历史网站。读取时验证主机名，完整 URL 或损坏值按解码错误报告。清除过期正文仍保留网站元数据，删除整条记录时一并删除。原始 AX URL 继续仅用于内存中的原目标校验，不提供给模型。

## 事务与并发

并发由 GRDB 承担：文件模式用 `DatabasePool`（WAL，读不被写阻塞，后台清理不会卡住正在列出记录的界面），内存模式用 `DatabaseQueue`。对外只有两个入口：`write` 与 `read`。GRDB 7 的写事务默认取 IMMEDIATE 锁，写锁在开头就要到手，冲突在调用者做完工作之前暴露，而不是在 COMMIT 时。

`Session` 不是 `Sendable`，无法逃逸出创建它的那次调用，所以「每条语句都在某个事务里」是结构上的，不靠约定。`Session.savepoint` 提供嵌套单元，让批量导入中的一条坏数据只回滚它自己。

`synchronous = NORMAL`：应用崩溃不丢已提交事务，断电可能丢最近几次提交。对润色历史这是合适的取舍——丢的是记录，正文还在目标应用里。

## 异常处理

所有 SQLite 结果码在一处翻译成 `PersistenceError`，调用者匹配语义而不是整数：`constraint`、`busy`、`corrupt`、`io`、`cannotOpen`、`schemaTooNew`、`migrationFailed`、`decoding`。三条纪律：

- 打开时就跑通 pragma，坏文件在 `Database(...)` 处失败，而不是在某次查询里。
- 迁移失败连版本号一起回滚，文件永远停在某个完整版本上。
- 比当前构建更新的结构直接拒绝写入，而不是降级打开后悄悄丢掉不认识的列。

## 保留与隐私

用户草稿是这个数据库里唯一敏感的东西，它的存活时间是调用方设定的策略，不是表结构的副作用。`RetentionPolicy` 有三个独立旋钮：整行的最大年龄、最大条数、正文的最大年龄。一次 `purge` 是一个事务：先按年龄删、再按条数裁、最后抹正文，顺序保证同一行不会既被计入删除又被计入抹除。`metadataOnly` 把正文年龄设为 0，只留统计。

数据库目录 0700、文件 0600；拒绝符号链接路径，避免数据库写入被重定向。

## 可扩展性、性能与可维护性

- 扩展：新增结构只能追加一个 `Migration`，已发布版本不再编辑——它创建的文件已经无法回头编辑。新增实体只需一个协议加一个实现；`MemoryRecordStore` 的存在是对抽象的持续检验，SQLite 能做而它做不到的事，就是 SQL 漏进契约的信号。
- 性能：数据规模是每天几十条记录，索引覆盖唯一的两个访问模式（按时间倒序、按技能加时间）。使用统计由记录聚合而来，不在技能行上冗余计数，删一条记录会自动修正统计，而不是留下一个偏高的数字。
- 可维护：没有 ORM 与反射，列名与实体的映射是显式的；改错列名会得到一个带列名的解码失败，而不是一个静默移位的值。存储用的枚举字符串是磁盘契约，从领域状态显式映射而来，重命名领域 case 不会改变已经写下去的数据。
