# Release runbook

The first candidate is `v0.2.4-preview.1`, Apple Silicon only. GitHub draft releases are review artifacts, not public downloads.

1. Read `readiness.md`; resolve licensing before public distribution. Review the intended Git tree and history for third-party material and private data. Keep parked evaluation files, outputs, databases and credentials out of Git.
2. Run `swift test`, then commit the exact source you intend to build. Confirm no live Dayi tasks, quit the app, then update its bundle and relaunch. Quitting clears in-memory undo. Swapping the bundle while an older process still lazily reads resources can leave it looking for a retired template; staging alone does not prevent that mismatch.
3. Run `zsh scripts/package-app.sh`. This creates .icns/resources, signs with Developer ID when available, and records source commit + dirty-state in the bundle. The release-preparation script rejects ad-hoc builds and dirty receipts.
4. Verify `codesign --verify --strict outputs/Dayi.app`. Check the icon in Finder/About and the idle menu bar, both appearances, then run synthetic target capture/write-back/undo checks. Do not claim untested client support.
5. With an explicitly configured notarization profile, create a submission ZIP using `ditto -c -k --sequesterRsrc --keepParent outputs/Dayi.app outputs/Dayi-notary.zip`, then submit with `xcrun notarytool submit outputs/Dayi-notary.zip --keychain-profile YOUR_PROFILE --wait`. Use notarytool log if rejected. Never put passwords or API keys in this repository or release notes.
6. After Apple accepts it, run `xcrun stapler staple outputs/Dayi.app`, `xcrun stapler validate outputs/Dayi.app`, and `spctl --assess --type execute --verbose outputs/Dayi.app`. ZIP the app again after stapling. A clean-machine/quarantined download check is still needed. No Gatekeeper-disabling instructions belong in installation docs.
7. Run `python3 scripts/prepare-release.py --tag v0.2.4-preview.1`. It creates the signed app ZIP, `release.json` and `SHA256SUMS.txt` under the ignored `outputs/releases/` directory. This script intentionally produces a private preview with unresolved public gates; it does not publish or silently mark a preview public-ready.
8. Sync the release tree onto the public `main` (see step 9) and wait for the public repository's CI on that commit; the private repository has Actions disabled. Package from a local checkout of the public commit so the build receipt names a public hash. Create/update the GitHub **draft**, target that commit, and attach the generated assets and release notes. Verify draft=true, prerelease=true, target SHA and asset checksums/download integrity.
9. After the release is public, run `zsh scripts/update-appcast.sh <tag>`. It signs the archive with the EdDSA key in the login keychain, adds the entry to `site/appcast.xml`, and keeps a copy of every published zip under the ignored `outputs/releases/appcast/`. Commit `site/appcast.xml` and sync it to the public `main`; GitHub Pages serves it at the `SUFeedURL` in Info.plist. Installed copies from build 9 onward see the update on their next check.
10. Only after owner approval and all gates are cleared: publish a properly versioned release. The public source repository `reny1cao/dayi` is seeded from the squashed `public-history` branch (`git checkout --orphan public-history && git commit` from the release tree; for later changes, commit the new tree on top of the public `main` instead of re-seeding, so release tags stay on the branch), not the private repository made public. Review immutable-release settings before publication. Do not change repository visibility or rewrite shared history as a side effect of packaging.

For another candidate, use a new preview number. Keep the source commit, build receipt, signature, notarization result and artifact hashes together. Changes after packaging require a new build; do not upload a stale binary against a newer commit.
