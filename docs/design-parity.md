**偏差 1（唯一的尺寸偏差）**：原文列最小宽 **120，不是稿上的 200**。算术原因：26+96+130+54+76 = 382 固定列，加边栏 190 与检查器最小 260，在 720 最小宽下放不进 200 的原文列。取舍是「原文列压到一行短句」而不是「窗口开不到 720」。另配 `inspectorMinWindowWidth = 960`：低于 960 时检查器自动收起，让原文列回到 200 以上。理想宽仍是 200。

**偏差 2（搜索框，用户 2026-09-10 要求）**：稿上搜索框常驻展开、固定 210 宽。改为**默认收成一枚放大镜图标**，⌘F 或点击展开并接管键盘。收回的条件有两条：编辑结束，或**窗口内任何落在输入框之外的点击**。两条都只在框是空的时候生效——有查询时保持展开，否则列表被筛短了却看不见原因。清空走 `NSSearchField` 自带的取消按钮或 Esc，清空之后下一次点到别处就收回。

（一枚「清空并关闭」的 x 试过又撤了，2026-09-10。）

「点击工具栏不收回」这条是真 bug，根因是 AppKit 的按钮在未开全键盘控制时**不接管 first responder**，所以点 排序 或 检查器 时 `controlTextDidEndEditing` 根本不触发。修法是一个 `NSEvent.addLocalMonitorForEvents(.leftMouseDown)`，命中测试落在输入框之外就收回，事件原样放行。实测（合成 CGEvent 真实点击，AX 的 press 动作不产生鼠标事件、验不出来）：点 检查器 立即从 4 个控件收回到 3 个；点 排序 菜单时因为菜单在跑模态事件循环，收回等到菜单关闭后生效——这也是对的，菜单还开着就抽掉它的锚点更糟。展开宽度不是 210，而是 `inspectorWidth − toolbarTrailingInset`（300 − 8），让**搜索框左边缘正好落在检查器列的左边界上**，不越界进表格区。

尾部是**三个独立的** `ToolbarItem`。试过合成一个并把宽度钉死，两个按钮确实不动了，但 macOS 会给每个工具栏项画一层容器背景——一个宽到装得下展开输入框的项，在收起时会把那层背景连同空着的那半一起画出来，成了一条长长的空胶囊，控件挤在右端。拆成三项后每个控件有自己的容器，也就是稿上的样子。

尾部工具栏项是从窗口右缘往里排的，所以左边那一项改变宽度时，两个按钮到右缘的距离不变。图标与输入框在项内用 `ZStack` 叠放而不是 `if`/`else` 换位：后者在交叉淡出期间两个子视图都还占着布局，那段多出来的宽度会推开旁边的东西。

**位移发生在过程中，不在端点**——这是把动画临时调到 2 秒逐帧量出来的。合成一项、宽度渐变的那一版，端点完全一致，但动画途中两个按钮先向左跳 62pt 再滑回来（到窗口右缘的距离：静止 103/48，途中 165→139→122→112→108 与 109→83→66→57→52）。拆成三项后同样的采样：排序 `108..52`、检查器 `52..4`，五次中间采样与两个端点**完全相同**。

另一个只有录屏才看得见的问题：输入框被移除时，AppKit 会去找下一个响应者、落在工具栏上，于是给三个项整体画一圈焦点环——一条横跨整个工具栏的蓝色胶囊，比输入框多活半秒。`dismantleNSView` 里在移除前把 first responder 交还给窗口，环就不出现了。

展开宽度 `Metric.searchOpenWidth = 188` 是量出来的常量，不是算出来的：排序与检查器现在是独立项，AppKit 给它们的宽度和项间距都是系统说了算。校验方式是「展开时输入框左缘落在检查器列边界上」——实测窗口右缘 1525、边界 1225、输入框左缘 1225。换 SDK 后若工具栏尺寸变了，重量一次这个数。那 8pt 是 AppKit 给尾部工具栏组的内缩，用无障碍框实测出来的（窗口右缘 1255，组内容右缘 1247）；改完复测：窗口右缘 1225、检查器边界 925、搜索框左缘 925，正好对齐。

**展开／收起没有动画，而且做不出来。** `ToolbarItem` 的内容托管在窗口自己的视图树之外，加在它布局上的隐式动画根本不跑——把时长临时拉到 2 秒、用 60fps 录屏逐帧看，宽度仍然是**一帧之内**变完的。之前加的 `.animation` 唯一的效果是多出一帧「用新几何画旧图标」的残影（一枚放大镜闪在最左边），所以整段删掉了。开合各占一帧，这也正好是两个按钮**绝对不会**动的唯一保证。

副作用是好的：DESIGN.md §10「只有四个动画」重新成立，不再有第五个——内容先落定，宽度后到，所以读起来是「盒子开了」而不是「有东西滑进来」。这段宽度是全应用位移最大的一处，也是唯一一处看得见的滑动会像 bug 的地方。Reduce Motion 下两者都归零，切换即时。**这仍是 §10「只有四个动画」之外的第五个**；要严守 §10 就把那行 `.animation` 和 `searchContentTransition` 一起删掉。

## 6.5 表格滚动（2026-09-10）

用 `sample` 在合成滚动期间抓主线程，不靠感觉。主线程**忙碌采样数从 115/2135 降到 7/2179**（同一段滚动，约 16 倍）。改了五处：

| 改动 | 为什么 |
|---|---|
| 行高从 `minHeight` 改成写死（`minHeight == maxHeight`）| 能长高的单元格必须先被测量，行才能排版，而表格每滚进一行就要重新问一次。§3 规定每行就是一行文字，行高是事实不是协商结果——这是最大的一处 |
| 六列的文字改为**建对象时算一次**（`previewText`／`modelText`／`durationText`／`timeText`／VoiceOver 摘要）| `Calendar.isDateInToday` 和 `DateFormatter.string(from:)` 都不便宜，之前是每格每帧各算一遍。item 只在数据变化时重建，所以这笔开销从每帧变成每次变化 |
| 悬停跟踪从**每行 6 个**减到 1 个 | 六列各挂一个 `onHover` 就是六个 `NSTrackingArea`，滚动时行在动，AppKit 逐个重建 |
| 悬停状态从表格的 `@State` 挪进单元格自己的 `@State` | 挂在表格上，任何一次悬停变化都要过整个表格的 body |
| 边栏各应用计数加缓存 | 之前每次读都对整份日志重新分组 + 排序 |

**行为收窄一处**：悬停出现的两枚快捷按钮，现在要指针落在「原文」列上才出现，之前整行任意位置都行。按钮本来就浮在原文列上，且原文是最宽的一列。

**没能可靠测到的**：帧率。用 `screencapture -v` 录屏数冻结帧，同样的操作三次跑出 10%／12%／61%，录制器自己的出帧节奏就把信号淹了，所以这里不给帧率数字。

### 6.5.1 后续复测与方案替换（2026-09-10）

用户录屏未通过上一轮滚动体验验收。通过探针/KVO 修改 SwiftUI 内部表格行高的补丁已撤销；该补丁的采样结果不代表用户体验已经解决。

中间活动表格现改用通过 `NSViewRepresentable` 持有的原生 `NSTableView`，由 AppKit 提供滚动、复用与选择，不再干预 SwiftUI 管理的内部表格。六列、固定行高、排序、多选、右键与原文列悬停操作保留；原生悬停按钮显示时收窄文字区域，不再用渐变覆盖文字。

版本核实、Apple 官方写法、同数据对照、输入焦点误报和前置失败记录缺口，以及实际验证边界，见 [活动表格、输入焦点与失败记录复查](scrolling-and-capture-review.md)。

## 7. 主链路未被动过

`⌃⌥P` 捕获 → 润色 → 写回 → `⌃⌥Z` 撤回这条链路只有一处新增，且是只读的：`AXTextTarget` 多记了 `role` / `isWeb` / `capturedRange` 三个值，供检查器「目标」段解释「为什么这个结果写不回去」。捕获、写入、冲突判定、撤回逻辑一行未改。

`GlobalHotKey` 改成可重绑：默认仍是 ⌃⌥P / ⌃⌥Z；重绑失败会**先回滚到原绑定再抛错**，不会出现「两个键都没注册」的状态。

核对过的面：活动窗口（边栏计数、六列、状态图标、选中态、检查器五段与 diff 标注、footer）、菜单栏面板「就绪」版、完整主菜单（§9 的十一条快捷键全部到位，`⌘Z` 确认未绑定）、设置 通用 页、设置 模型 页（服务商胶囊、实测耗时取值、220 宽字段、高级折叠、底部工具条）。实测数字确认取自 `docs/status.md`：模型页显示「2026-09-10 实测 · 1.6–4.0 秒」。
